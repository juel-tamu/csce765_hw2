  The setup

  {"action":"READ","path":"notes.txt"}
  The scenario has three parts: a sender encrypts the command, a relay (the
  attacker in the middle) passes it along, and a receiver decrypts it and acts
  on it.

  Attack 1: Bit-flipping (tampering without the key)

  AES-CTR builds a keystream from the key and IV, then XORs it with the
  plaintext:

    C = P ⊕ KS

  says READ at a fixed position. That's bytes 11–14, because {"action":" is 11
  characters long. To turn READ into another 4-byte word such as EXEC, the relay
  XORs those ciphertext bytes:

    C' = C ⊕ (P ⊕ P') → C' ⊕ KS = P'

  The receiver decrypts without any error and gets
  {"action":"EXEC","path":"notes.txt"}.

  "Show the XOR relation" means printing the bytes to prove that C ⊕ C' = P ⊕ 
  P'. In other words, the change in the ciphertext is exactly the change in the
  plaintext, and the keystream cancels out.

  number, nonce tracking or MAC, so it decrypts and "executes" the command both
  times. Your script should show it being processed twice, for example with a

⏺ For Task 3 you build secure_record.py: a sender seals a message into a
  protected record, and a receiver opens it, refusing anything that was tampered
  with, replayed or sent in the wrong direction.

  The record format

  record = header (15 bytes) || ciphertext || tag (32 bytes)

  header = version(1) | direction(1) | sequence(8) | message_type(1) | 
  ciphertext_length(4)
  iv     = session_id(8) | sequence(8)          # 16 bytes, rebuilt by the 
  receiver
  tag    = HMAC-SHA-256(K_mac, header || iv || ciphertext)

  - Pack the header with struct.pack(">BBQBI", version, direction, seq, 
    msg_type, len(ct)). The > gives big-endian byte order, and the result is 15
    bytes.
  - The IV doesn't have to be sent. The receiver already knows session_id and
    can read sequence from the header. The tag still covers the IV.
  - Pick constants for direction, e.g. 0 = gateway→node, 1 = node→gateway.

  State to keep

  Each endpoint needs per-direction state. For example, a small class holding:
  - send_key_enc, send_key_mac, send_seq = 0, send_direction
  - recv_key_enc, recv_key_mac, recv_seq = 0, recv_direction
  - session_id

  The gateway sends with the g2n keys and receives with the n2g keys. The node
  does the reverse. That covers "separate keys in each direction".

  seal(state, msg_type, plaintext)

  1. seq = state.send_seq. Refuse to send if it would go past 2⁶⁴−1.
  2. iv = session_id + seq.to_bytes(8, "big")
  3. Encrypt with AES-256-CTR using send_key_enc and iv.
  4. Build the header.
  5. tag = HMAC(send_key_mac, header + iv + ct)
  6. state.send_seq += 1. This means you never reuse an IV under one key.
  7. Return header + ct + tag.

  open_record(state, record): the order matters

  1. Length checks: the record must be at least 15 + 32 bytes, and
     ciphertext_length must match the actual size. Otherwise reject.
  2. Parse the header. Check version is the one you expect.
  3. Direction check: it must equal recv_direction. This rejects reflected
     records.
  4. Rebuild the IV from session_id and the header's sequence.
  5. Verify the MAC before decrypting. Use the library's constant-time check:
  from cryptography.hazmat.primitives import hmac, hashes
  h = hmac.HMAC(recv_key_mac, hashes.SHA256()); h.update(header + iv + ct)
  h.verify(tag)   # raises InvalidSignature on mismatch; don't compare with ==
  6. Sequence check: it must equal state.recv_seq exactly. This rejects replays
     and reordered records.
  7. Only now decrypt, then state.recv_seq += 1, then return the plaintext.

  On any failure: raise an exception (e.g. a custom RecordError("bad MAC")) and
  return no plaintext, not even part of it. Don't advance recv_seq on failure.
  Specific error messages will make your Task 4 tests easier to assert on.

  One subtlety worth putting in your report

  AES-CTR in the cryptography library treats the whole 16-byte IV as a counter
  and increments it for every 16-byte block. Because the IV is session_id || 
  seq, a message with seq=0 that is longer than 16 bytes uses the counter blocks
  …||0, …||1, and the message with seq=1 starts at …||1. The keystream
  overlaps. The spec's commands are short, but it's a real weakness of this IV
  layout. Mention it in your security note or ask your instructor; don't change
  the spec's format on your own. This also connects directly to the note's "why
  CTR requires unique IVs" point.

  Quick self-test before Task 4

  Using random keys: seal → open works in both directions. Flip one ciphertext
  byte, one header byte, or one tag byte and opening should fail. Open the same
  record twice and the second attempt should fail. Feed a g2n record to the
  gateway's receive side and it should fail.

  What item 3 asks for

  1. Load the group file. Read ffdhe3072.pem, the file you generated in Lab

  generator g). You don't pick your own numbers.

  2. Build one transcript. The transcript is a single byte string recording
  everything that matters about this handshake:
  - the protocol label CSCE465-HS-v2 (which protocol and version this is)
  - the group identifier ffdhe3072 (which DH group)
  - both identities (who is talking)
  - both DH public values (the key shares)
  - both nonces (what makes this session unique)

  Both parties must build exactly the same bytes. Each one signs a hash of it,
  so if one field differs by one byte, the signatures won't verify. "Canonical"
  means there is only one correct way to encode a given set of values.

  3. Use length prefixes, not plain concatenation. This is the main point of
  item 3. If you just glue the fields together, different field values can
  produce the same bytes. For example, with identities:
  id_G = "gate",    id_N = "waynode"   →  "gatewaynode"
  id_G = "gateway", id_N = "node"      →  "gatewaynode"
  Both give identical bytes, so both give the same hash and the same signature.
  An attacker could take a signature made for one meaning and present it as the
  other.

  With a 4-byte big-endian length before each field, the two cases can no longer
  collide:
  00 00 00 04 "gate"    00 00 00 07 "waynode"
  00 00 00 07 "gateway" 00 00 00 04 "node"
  Now the bytes are different, so each set of values has exactly one encoding.

  In code, encoding is one line per field:
  def encode(fields):
      return b"".join(len(f).to_bytes(4, "big") + f for f in fields)

  4. Reject a bad length before hashing. When you read a transcript back, you
  parse it: read 4 bytes as a length, take that many bytes, and repeat. If a
  declared length is larger than the bytes that are left, or bytes are left over
  at the end, or the field count is wrong, the transcript is malformed. Throw
  an error and never hash it. That way a malformed transcript can never reach
  the signing or verification step.
  def decode(data, expected_fields=8):
      fields, i = [], 0
      while i < len(data):
          if i + 4 > len(data): raise HandshakeError("truncated length")
          n = int.from_bytes(data[i:i+4], "big"); i += 4
          if i + n > len(data): raise HandshakeError("bad declared length")
          fields.append(data[i:i+n]); i += n
      if len(fields) != expected_fields: raise HandshakeError("wrong field 
  count")
      return fields

⏺ Here's the idea without code.

  The transcript: a shared receipt of the conversation

  Think of the handshake as a short conversation:
  - Gateway: "I'm gateway-01, here's my DH share and a random nonce."
  - Node: "I'm node-01, here's my DH share and a random nonce."

  After those two messages, both sides hold the same set of facts: which
  protocol, which group, who the two parties are, both DH shares, and both
  nonces.

  The transcript is those facts written down in an agreed format, like a receipt
  listing everything that happened. Both parties write their own copy. If
  nobody tampered with anything, the two copies are byte-for-byte identical.

  Why bother? Each party signs the receipt. A signature says "I confirm this
  exact conversation happened." If an attacker swapped a DH share, changed a
  nonce or substituted an identity, the two receipts would differ, and the
  signature one side made won't match what the other side wrote down. The
  tampering gets caught.

  The length-prefix rule only makes sure there's exactly one way to write the
  receipt, so nobody can make it say two different things.

  The role: who is signing

  Here's the catch: both sides sign the same receipt. So the gateway's signature
  and the node's signature are both statements about identical content.

  The role is a short tag added in front of the receipt before signing, which
  changes the statement:
  - Gateway signs: "As the gateway, I confirm this conversation."
  - Node signs: "As the node, I confirm this conversation."

  Each side checks that the peer's signature says the peer's role, not its own.

  Why it matters (reflection): Without the role, a signature only says "I
  confirm this conversation." An attacker could take the gateway's own signature
  and hand it back to the gateway as if it were the node's reply. In this
  assignment the keys are different, so the gateway would usually catch that
  anyway. But in real systems, the same key or identity can sometimes act in
  either role, and then a reflected message gets accepted. The role tag removes
  that possibility entirely. A signature made as the gateway can never be
  accepted as one from the node.

  Putting it together

  ┌────────────┬─────────────────────────────────────────────────────────────┐
  │    Part    │                   The question it answers                   │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Transcript │ What conversation is being confirmed?                       │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Role       │ Who, in which position, is confirming it?                   │
  ├────────────┼─────────────────────────────────────────────────────────────┤
  │ Signature  │ Proof that a specific key holder really made this statement │
  └────────────┴─────────────────────────────────────────────────────────────┘

  Analogy: a contract (the transcript) that both buyer and seller sign. Each
  signature line is labelled "Buyer" or "Seller" (the role). You can't cut out
  the seller's signature and paste it onto the buyer's line.

❯ wouldnt transcript hash validation just check mod of 4?                       
⏺ No. Checking whether the total length is a multiple of 4 doesn't work, for two
  reasons:

  1. The fields aren't multiples of 4. Only the length prefixes are 4 bytes. The
  fields after them have their own sizes:
  - CSCE465-HS-v2 → 13 bytes
  - ffdhe3072 → 9 bytes
  - identities → whatever you chose, e.g. gateway-01 is 10 bytes
  - DH values → 384 bytes each
  - nonces → 16 bytes each

  So a perfectly valid transcript usually has a total length that isn't
  divisible by 4, and a mod-4 check would reject it.

  2. A total-length check can't see inside. Even if the total happened to be
  right, it says nothing about whether each declared length matches the field
  after it. A transcript with one prefix too big and another too small can still
  have the right total.

  What validation actually means: walking through the transcript the way a
  reader would:
  1. Read 4 bytes → that's the length of the next field, say n.
  2. Are there at least n bytes left? If not, the declared length is wrong, so
     reject.
  3. Skip over those n bytes. That's the field.
  4. Repeat until you reach the end.
  5. At the end, check that you landed exactly on the last byte, with nothing
     left over and nothing missing, and that you found exactly 8 fields.

  Optionally you can also check the content: field 1 is the expected label,
  field 2 is ffdhe3072, the DH values are 384 bytes and the nonces are 16 bytes.

  Small example. Suppose the second field declares a length of 20, but only 9
  bytes (ffdhe3072) actually follow before the next prefix. Your reader takes 20
  bytes, which swallows part of the next field, so every field after that is
  misread. Either you run out of bytes or the field count comes out wrong, so
  the transcript gets rejected. A mod-4 check would have missed this.

  The decode sketch I showed earlier does this walk, if you want to compare it
  against your version.

❯ explain recordstate                                                           

⏺ RecordState is each endpoint's memory for the secure channel. seal and
  open_record are plain functions, so on their own they can't remember anything
  between calls. But the protocol needs memory: which keys to use, which
  sequence number comes next, and which direction is "mine". RecordState holds
  that.

  Each side gets its own RecordState: the gateway has one and the node has one.

  What's inside

  For sending:
  - send_enc: the AES key for encrypting what I send
  - send_mac: the HMAC key for tagging what I send
  - send_dir: the direction byte I put in my headers
  - send_seq: the sequence number for my next outgoing record

  For receiving:
  - recv_enc, recv_mac: the keys for decrypting and checking what I receive
  - recv_dir: the direction byte I expect in incoming headers
  - recv_seq: the sequence number I expect next

  Shared:
  - session_id: the first half of every IV

  Why the gateway and node fill it in as mirror images

  The handshake gives both sides the same four keys. A channel has two one-way
  lanes:
  - gateway → node lane: uses the g2n keys and direction 0
  - node → gateway lane: uses the n2g keys and direction 1

  The gateway sends on the g2n lane and receives on the n2g lane. The node is
  the opposite. So the gateway's send_* fields equal the node's recv_* fields,
  and the reverse. That's why the class picks keys based on role.

  How it changes over time

  Only the two counters change. Everything else is fixed once the handshake is
  done.

  gateway seals msg A     → gateway.send_seq: 0 → 1
  node opens msg A        → node.recv_seq:    0 → 1
  gateway seals msg B     → gateway.send_seq: 1 → 2
  node opens msg A again  → header says seq 0, node expects 1 → rejected 
  (replay)

  The sender's send_seq and the receiver's recv_seq for the same lane move in
  lockstep. As long as they match, records are accepted. Any replay, skipped
  record or reordering breaks the match and gets rejected. And because the send
  counter only ever goes up, the IV session_id || seq never repeats under the
  same key.

  How each field maps to a Task 3 requirement

  ┌───────────────────────────────────────┬───────────────────────────────┐
  │              Requirement              │     Field that handles it     │
  ├───────────────────────────────────────┼───────────────────────────────┤
  │ Separate keys in each direction       │ separate send_* / recv_* keys │
  ├───────────────────────────────────────┼───────────────────────────────┤
  │ Sequence numbers start at zero        │ both counters start at 0      │
  ├───────────────────────────────────────┼───────────────────────────────┤
  │ Never reuse an IV                     │ send_seq only increases       │
  ├───────────────────────────────────────┼───────────────────────────────┤
  │ Expect the exact next sequence number │ recv_seq                      │
  ├───────────────────────────────────────┼───────────────────────────────┤
  │ Reject the wrong direction            │ recv_dir                      │
  └───────────────────────────────────────┴───────────────────────────────┘

  So RecordState is basically "everything this endpoint knows about the
  channel". seal and open_record read it, and they update the counters only when
  an operation succeeds.

❯ explain to me how open_record should work                                     

⏺ open_record is the receiver's gatekeeper. It takes raw bytes off the "wire"
  and either returns the plaintext, if everything checks out, or raises an error
  and reveals nothing. The order of the checks is what makes it secure.

  What arrives

  | header (15 bytes) | ciphertext (ct_len bytes) | tag (32 bytes) |

  The steps, in order

  1. Check the overall size.
  If the record is shorter than 15 + 32 bytes, it can't even contain a header
  and a tag, so reject it. This prevents crashes when slicing.

  2. Split and unpack the header.
  - header = record[:15]
  - tag = record[-32:]
  - ct = record[15:-32]

  Unpack the header into version, direction, seq, msg_type and ct_len.

  3. Sanity-check the header fields.
  - version must be what you support.
  - ct_len must equal len(ct). If it doesn't, the record is malformed.

  4. Check the direction.
  It must equal state.recv_dir. This catches a record reflected back to its
  sender. For example, the gateway's own outgoing record gets fed back to the
  gateway.

  5. Rebuild the IV.
  iv = state.session_id + seq.to_bytes(8, "big"). The IV isn't sent, so you
  rebuild it from what you know plus the seq in the header.

  6. Verify the MAC. This is the most important step.
  Compute HMAC-SHA-256 with state.recv_mac over header + iv + ct and check it
  with h.verify(tag). If it fails, someone changed the header, the ciphertext or
  the tag, so reject.
  - It uses the library's constant-time comparison. A normal == can leak,
    through timing, how many bytes matched.
  - It runs before decryption. You never decrypt or act on data you haven't
    confirmed is genuine.

  7. Check the sequence number.
  seq must equal state.recv_seq exactly:
  - Lower means a replay (or an old record).
  - Higher means a record was skipped or reordered.

  Either way, reject. Doing this after the MAC means you know the seq value is
  authentic and not attacker-chosen garbage.

  8. Decrypt.
  AES-256-CTR with state.recv_enc and the IV.

  9. Advance the counter and return.
  state.recv_seq += 1, then return the plaintext (and msg_type if you want).

  Error handling rules

  - Every failure raises an exception (e.g. RecordError("bad MAC"),
    RecordError("replay")). Never return None or partial data.
  - No state change on failure: recv_seq moves only at step 9. Otherwise an
    attacker could send junk to push your counter forward and get real records
    rejected.
  - No plaintext on failure: since decryption happens last, there's nothing to
    leak.

  Why this order

  cheap structural checks → direction → MAC → sequence → decrypt → update state
  - The structural checks make sure parsing is safe.
  - The MAC proves the bytes are authentic.
  - Only authentic data can affect your state or get decrypted.

  Quick mental test

  ┌─────────────────────────────────┬───────────────────────────────────────┐
  │     What the attacker does      │         Step that rejects it          │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Flips a ciphertext bit          │ 6 (MAC)                               │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Changes seq in the header       │ 6 (MAC, since the header is           │
  │                                 │ authenticated)                        │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Changes the direction byte      │ 4, or 6 if it was changed to look     │
  │                                 │ correct                               │
  ├─────────────────────────────────┼───────────────────────────────────────┤
  │ Sends the same record twice     │ 7 (sequence)                          │
  ├─────────────────────────────────┼───────────────────────────────────────┤

  │ sender                          │                                       │

  tampered header, replay and reflection.
